### 1.2 当前痛点（需前置解决）

以下问题需要在任何大规模新功能开发前优先处理：

| # | 痛点 | 影响 | 严重度 |
|---|------|------|--------|
| P1 | **无统一的单位/量纲系统** | 所有参数语义模糊（"最大速度"到底是多少像素/秒？），新功能开发时每个数值都是"拍脑袋"设定，无法保证仿真物理一致性 | **阻塞级** |
| P2 | **ParamDef 仅支持 float 类型** | 年龄、性别、状态枚举等新参数必然是非 float 类型（int、bool、enum），当前架构无法直接注册这些参数，Bug 2.8 已证明强制 cast 有风险 | **阻塞级** |
| P3 | **个体缺少状态机** | 所有个体每帧执行全部行为逻辑，无法区分"正在战斗"和"正在觅食"的个体。新增战斗/哺乳/巢穴等系统会进一步加剧逻辑混杂 | **高风险** |
| P4 | **FlockParams 结构体线性膨胀** | 目前已有 ~45 个字段，新增年龄/体型/疲劳/记忆/仇恨等将使结构体突破 100 字段，编译依赖和参数管理都会失控 | **高风险** |
| P5 | **Simulation::update() 单函数过长** | 已有 ~700 行，一个循环内混合 Reynolds、捕猎、觅食、放牧、施肥、繁殖。新增战斗/内斗/防御协作将使此函数突破 1500 行，不可维护 | **高风险** |
| P6 | **无配置持久化** | 所有参数仅存于内存，关闭即丢失。80 项新需求意味着远超手动调参的复杂度上限 | **中风险** |
| P7 | **性能日志同步 I/O** | 每 250ms 磁盘写入阻塞 UI 线程，虽影响轻微但不专业 | **低风险** |

## 二、前置解决方案

### 2.1 P1 - 统一单位/量纲系统（建议最先实施）

**方案**：创建 `src/core/WorldConstants.h`，锁定所有基础物理常量

```cpp
// 空间基准
constexpr float PIXELS_PER_METER = 5.0f;      // 1 米 = 5 像素
constexpr float METERS_PER_PIXEL = 0.2f;

// 时间基准
constexpr float SIM_HOURS_PER_REAL_SEC = 1.0f;  // 1 现实秒 = 1 模拟小时
constexpr float SIM_DAYS_PER_REAL_SEC = 1.0f / 24.0f;

// 类型安全的速度/距离量纲包装
// PixelDistance, SimTime, SimSpeed 等强类型别名
```

**配套**：在 ParamDef 中新增 `unitHint` 字段（如"px/s"、"m/s"、"sim-hours"），UI 标签自动显示单位。滑块标签从 `最大速度 (Max Speed)` 升级为 `最大速度 50 px/s (Max Speed)`。

**工作量**：约 2-3 小时，代码改动集中在 ParamDef + MainWindow 参数注册处。

### 2.2 P2 - ParamDef 类型标记扩展

**方案**：在 `ParamDef` 中引入类型枚举，分支处理 float / int / bool

```cpp
enum class ParamType { Float, Int, Bool };

struct ParamDef {
    ParamType type = ParamType::Float;  // 默认保持向后兼容
    union {
        float defaultFloat;
        int   defaultInt;
        bool  defaultBool;
    };
    // readFrom/writeTo 根据 type 分支，不再用 reinterpret_cast<float*>
};
```

**替代方案（推荐）**：所有可调参数保持 float，新增的 int/bool 参数与现有参数分离——int/bool 在 `FlockData.h` 中定义但不通过 ParamRegistry 管理，而是在 MainWindow 中手动创建 QSpinBox/QCheckBox。这样 ParamDef 无需改动，零风险。只有在 int/bool 参数数量 > 5 时才值得扩展 ParamDef。

**推荐**：先采用替代方案（手动控件），需求清单中的年龄阶段数（enum）、性别（bool）、边界模式（enum）等完全可以用 QComboBox/QCheckBox 实现，暂不扩展 ParamDef。

### 2.3 P3 - 个体状态机

**方案**：在 Simulation 中引入简单的优先级状态机（平面，非层次）

```
优先级：生存本能 > 社会本能 > 资源竞争 > 社交本能

状态枚举：
  DEAD, IDLE, FLEEING, HUNTING, FORAGING, RESTING,
  MATING, FIGHTING, DEFENDING, NURSING

转换规则（代码化，不引入重型 FSM 库）：
  - 任意状态 → FLEEING，当 predatorDistance < fearRadius
  - IDLE → FORAGING，当 hunger < threshold
  - FORAGING → HUNTING，当 preyVisible && hunger < killThreshold
  - IDLE → MATING，当 mateNearby && reproductionReady
  ...
```

**数据结构扩展**（SoA）：
```cpp
// FlockData 新增数组
std::vector<int8_t> m_state;       // 状态枚举，1 字节
std::vector<float> m_stateTimer;   // 状态持续时间
```

**关键**：不是"每帧检查所有规则选一个执行"，而是"每帧只执行当前状态对应的规则子集"。这避免了 Simulation::update() 的无限膨胀。

**工作量**：约 4-6 小时。需重构 Simulation::update() 主循环，将逻辑从单一巨大循环拆分为 N 个状态处理函数。这是**最重要的架构改进**，直接影响后续所有需求模块的实施复杂度。

### 2.4 P4 - FlockParams 分层拆分

**方案**：将 FlockParams 按功能域拆分为多个子结构体

```cpp
struct MovementParams   { maxSpeed, weightSpeedPenalty, hardCollisionRadius; };
struct PerceptionParams { separationRadius, alignmentRadius, cohesionRadius;
                          separationWeight, alignmentWeight, cohesionWeight; };
struct HungerParams     { decayRate, speedMin, speedMax, flashThreshold,
                          forageRange, forageWeight, forageHungerThreshold;
                          invertHungerSpeed; };
struct PredationParams  { chaseSuccessBase, escapeSuccessBase, chaseRange,
                          predationMinHunger, predationKillHunger, ...; };
struct ReproductionParams { minOffspring, maxOffspring, interval, ...; };
struct BodyParams       { maxWeight, minWeight, weightGainPerKill, ...; };

struct FlockParams {
    MovementParams     movement;
    PerceptionParams   perception;
    HungerParams       hunger;
    PredationParams    predation;
    ReproductionParams reproduction;
    BodyParams         body;
    BoundaryParams     boundary;
    // ... future additions
};
```

**对 ParamRegistry 的影响**：`fieldOffset` 需要嵌套计算 `offsetof(FlockParams, hunger) + offsetof(HungerParams, decayRate)`，或改用 `float*` 成员指针。建议保持简单——拆分了结构体但保留直接 float 引用用于注册。

**工作量**：约 2-3 小时，主要是结构体重组 + 引用更新。

### 2.5 P5 - Simulation::update() 模块化拆分

**方案**：将单一大循环拆分为独立方法

```cpp
void update(float dt) {
    decayHunger(dt);
    rebuildGrids();
    computeFlocksForces();    // Reynolds + inter-flock
    computePredation();       // 捕猎判定
    computeForaging();        // 觅食（复用 PlantSpatialHash）
    computeGrazing();         // 进食
    computeFertilization();   // 施肥
    computeReproduction(dt);  // 繁殖
    integrate(dt);            // 位置/速度积分
    updatePlants(dt);
    cullDead();
}
```

每个子方法内部按状态分支（依赖 P3 状态机）。

**工作量**：约 2-3 小时。

### 2.6 P6 - 配置持久化

**方案**：JSON 序列化 FlockParams + PlantParams + 群体关系

```cpp
// 使用 QJsonDocument + QJsonObject，无额外依赖
void saveConfig(const QString& path);  // 另存为 .biodcfg 文件
void loadConfig(const QString& path);  // 加载配置
```

**文件格式**：`.biodcfg`（本质上是一个 JSON 文件，自定义后缀用于文件关联）

**工作量**：约 2 小时。

## 三、需求评价矩阵

对 [需求清单规划.md] 中 12 个模块、80 条需求逐一评价：

| 评价标记 | 含义 |
|---------|------|
| **A** | 合理且可立即实施（当前架构支持，ROI 高） |
| **B** | 合理但需前置条件（依赖 P1-P6 某几项） |
| **C** | 合理但工程量大（需独立里程碑） |
| **D** | 远期/概念性（暂不讨论实施方案） |
| **?** | 建议搁置或重新评估 |

### 3.1 核心行为与生理系统（模块一）—— 10 项

| 需求 | 评价 | 理由 |
|------|------|------|
| 年龄系统 | **B** | 需状态机(P3) + FlockData 扩展，设计合理 |
| 自然衰老死亡 | **B** | 同上，逻辑简单（年龄 > 上限 → dead） |
| 体型系统 | **B** | 现有 weight 系统已为 0.5-2.0 范围留了接口，可直接扩展 |
| 疲劳系统 | **B** | 需状态机(P3)，设计合理 |
| 性别二态性 | **B** | 现有 male/female 已区分着色，属性差值自然扩展 |
| 记忆系统 | **C** | 需每个体维护事件队列（N×M 内存），性能影响需评估 |
| 仇恨/敌意系统 | **B** | 可复用现有的捕食者-猎物目标锁定，扩展为列表 |

| 妊娠/怀孕系统 | **B** | 依赖状态机(P3) + 繁殖系统扩展，设计合理 |

**模块一采用建议**：年龄、衰老、体型、疲劳、性别二态性、哺乳、妊娠——7 项 **B 级**，建议在 P1-P3 解决后作为第一批新功能实施。

## 五、建议搁置的需求

| 需求 | 理由 |
|------|------|
| 近亲繁殖惩罚 | 需血缘关系图，实现成本 vs 体验收益不成比例 |
| 护食行为/领地小团体 | 需动态空间领地计算，与现有简单空间模型冲突 |
| 食物发现者优势 | 需追踪植物发现者，数据结构开销大 |
| 排便与标记系统 | 信息素扩散需额外 GPU/CPU 资源 |
| 气候/天气/生物群落（模块九大部） | 独立大型子系统，应在核心行为系统完备后再启动 |

## 六、设计原则采纳

从需求清单中提炼出以下设计原则，应在所有开发中遵守：

1. **黄金法则**："个体可以竞争能量，但代码不能凭空创造能量" —— 所有资源转换（捕猎→饱腹、尸体→施肥、死亡→能量归还）必须有闭环审计
2. **决策优先级**：生存本能 > 社会本能 > 资源竞争 > 社交本能 —— 状态机转换规则以此排序
3. **SoA + 零堆分配**：所有新增属性必须加入 SoA 数组，工作缓冲区预分配
4. **渐进式复杂度**：优先实施能复用现有机制的扩展（如内斗=异群斥力的同群特例），避免白手起家
5. **先架构后功能**：Phase 0 完成前，不在主循环中新增任何行为逻辑
